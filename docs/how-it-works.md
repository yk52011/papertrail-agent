# PaperTrail 的工作原理

PaperTrail 把复现任务组织成“执行—观察—决策—再执行”的循环。模型负责提出动作，程序负责限制动作和核验结果；没有密钥时可以用规则策略演示同一套执行框架。

## 用一个真实运行的例子理解

自带 Sentiment Lab 的初始配置中，训练文件路径和文本字段名各有一个错误。

1. 系统复制项目，读取任务清单，保留原仓库。
2. 执行 `python train.py`，实际得到 `FileNotFoundError`，而非让模型猜测运行结果。
3. 从 README、配置和代码片段中检索有关 `train_path` 的依据，记录文件及行号。
4. 规则策略或模型提出将 `train_path` 改为 `data/train.json`。
5. 服务端确认该键和值属于任务清单允许的范围，才修改工作副本，并保存修改前后指纹。
6. 第二次运行发现 `KeyError: sentence`，重复检索与决策，将 `text_column` 改为 `text`。
7. 第三次运行完成真实的 TF-IDF 特征提取和逻辑回归训练，输出预测文件。
8. 独立核验器根据执行前载入的参考标签重新计算指标，检查输出是否满足预先约定的条件。

## RAG 在哪里发挥作用

项目资料按 40 行切成片段，相邻片段重叠 10 行。每段保留来源、行号和 SHA256。
恢复节点根据当前失败检索 BM25 匹配片段，将其与日志、配置和可选动作一并提供给决策器。

检索器负责找资料，决策器负责选择如何处理。检索到一段资料不保证决策正确；当前引用校验只确认引用属于本次检索结果，没有自动证明原文充分支持动作。
独立的资料问答路径还支持向量余弦检索，并用 RRF 融合词法与语义排名；恢复节点当前仅使用 BM25。

## LangChain 和 LangGraph 各自负责什么

- LangChain 对接模型，接收符合 Pydantic 模型的结构化恢复决策：错误类型、配置修改、原因和引用。
- LangGraph 根据任务状态选择下一节点，在失败后形成恢复循环，在成功、预算耗尽或无可支持动作时结束。
- SQLiteSaver 把图状态逐节点保存。动态 interrupt 可以在修改配置前暂停，下一进程用同一个任务 ID 继续。

它们不是分类模型，也不负责直接训练；训练由实验子进程里的代码完成。

## 为什么需要独立核验

“进程退出码为 0”“目录里有指标文件”“程序说得到 100%”都可能误报成功。

系统先移除工作副本里的旧目标产物，再要求本次产生合法 JSON；如果提供参考标签，还会检查预测 ID 全覆盖、无重复，并独立重算 Accuracy 和 Macro F1。程序上报的指标与重算结果不一致时直接拒绝。

这仍只验证产物契约，不能证明训练过程无数据泄漏或论文方法正确，因此不会自动宣称论文复现成功。

## 为什么恢复动作有边界

`task.json` 明确允许修改的配置键及候选值。模型不能扩大自己的权限，不能降低指标阈值，不能改参考标签或运行命令。每个任务还有尝试次数和时间预算，防止无限重跑。

规则模式适合展示已知故障的处理路径；真实模型的泛化效果需要另外接入服务，在留出的真实仓库任务上评测。
